# ADR 002: Docker Compose development environment

Status: accepted

## Context

Running the project needed the .NET SDK, a PostgreSQL server, hand-set secrets and a manual migration step. A new developer should be able to clone the repository and have the API and a database running with a few commands, without weakening any of the security rules added earlier.

## Decisions

**Compose runs three services: `postgres`, `migrate`, `api`.** Nothing else is added.

**Migrations run as a separate one-shot job, never from the API.** Phase 4 decided that the API must not change the schema at startup, and that still holds (no `Database.Migrate()`, no `EnsureCreated`). The `migrate` image is built from an EF Core *migrations bundle*: one self-contained executable containing every migration, on a minimal base image. Consequences:
- the API image contains no EF tooling, SDK or migration code path, and stays small;
- the schema change is a visible, separate step with its own log, and it fails loudly (the API does not start after a failed migration);
- it is idempotent, so running it on every `docker compose up` is safe, and it can also be run alone with `docker compose run --rm migrate`;
- the same bundle can later be run by a deployment pipeline against a real database.

A documented `docker compose run` command alone was rejected because it would make the first-run experience several manual steps and would let the API start against an unmigrated database.

**Secrets are required, never defaulted or generated by Compose.** `POSTGRES_PASSWORD` and `JWT_SIGNING_KEY` use `${VAR:?message}`, so Compose stops with a clear error if they are missing. The API's own startup validation of the signing key is unchanged. `.env.example` leaves the secrets empty on purpose; the helper scripts fill `.env` with random values. `.env` is git-ignored and is not part of the Docker build context, so it cannot be baked into an image.

**The build context is an allow-list.** `.dockerignore` excludes everything and re-includes only `src/` and the tool manifest, minus build output and local settings, so secrets, history and unrelated files never reach the build.

**The API runs as a non-root user with a locked-down container:** the unprivileged `app` user of the official .NET image, a read-only filesystem with a temporary `/tmp`, all Linux capabilities dropped and privilege escalation disabled. The .NET host is PID 1 (exec-form entrypoint), so `docker stop` shuts it down cleanly.

**Plain HTTP on 8080 inside the container.** TLS termination belongs to a reverse proxy or load balancer in a real deployment, which is out of scope here. Published ports bind to `127.0.0.1` only.

**Compose defaults to the Development environment** so the OpenAPI document and interactive reference are available locally. This is a Compose default only (`ASPNETCORE_ENVIRONMENT`); the image itself and the application's behaviour are unchanged, and `Production` still hides the documentation.

**Health checks follow what each check means.** PostgreSQL uses `pg_isready` for the configured database. The API uses `/health` (readiness: reachable and migrated), because "the process is up" is not the same as "able to serve requests". The official runtime image has no curl, so the check speaks HTTP with `bash`, avoiding an extra package in the image.

**PostgreSQL data lives in a named volume** that survives `docker compose down` and is deleted only by `down -v`.

## Consequences

- The only requirement to run the stack is a running Docker engine.
- The setup is for local development. Production needs TLS, secret management and a deployment pipeline, none of which exist yet.
- Changing `POSTGRES_PASSWORD` after the volume exists has no effect on the database (PostgreSQL reads it only when it creates the volume), which the troubleshooting section documents.
